# ai-probe

A tera plugin at level 3, generated by `tera plugin new ai-probe --template filing`:
tools, state and settings, a UI and events, and filing work.

- `main.go` — the plugin: the start contract, the SDK's serve loop with the web
  kit as its UI, and the configuration watched live.
- `tools.go` — `hello`, `note` and `token_status`, as the state template writes them.
- `filing.go` — `file_note`, which files a Work Order for the person the call is for.
- `settings.go` — the configuration, as the plugin decodes it.
- `web/`, `embed.go`, `events.go`, `watch.go` — the UI over tera and watching
  events, as the ui template writes them.
- `vault/.tera/` — the plugin vault: the `note` Work Order type and the tool its
  sessions run.
- `manifest.hcl` — what the plugin needs and offers: `serves { tools {} ui {} }`,
  the `on_behalf_of` grants, and the `config_schema`.

The plugin's binary embeds the app, so build it first:
`(cd ai-probe/web && npm install && npm run build)`.

## Run it, then pack it

From the directory that holds `ai-probe/`, where `tera plugin new` wrote it:

    (cd ai-probe && go mod tidy)
    tera plugin dev --dir ai-probe --approve read-for-a-person,file-for-a-person
    $EDITOR ai-probe/manifest.hcl
    tera plugin pack --dir ai-probe --url \
      'https://github.com/<owner>/ai-probe/releases/download/v${version}/ai-probe-${platform.os}-${platform.arch}.tar.gz'

`dev` runs the plugin on a local daemon under this manifest and the production
sandbox, and rebuilds and restarts it whenever you save. A grant the manifest
requests is approved for the run with `--approve`, as an installation approves it;
one left undecided keeps the plugin stopped, and dev names it. Each refusal it
prints names the manifest line that fixes it. See `tera plugin dev -h`.

`pack` validates the vault against the declared recipes level, builds one archive
per platform into `dist/`, writes the release manifest beside them (this manifest
plus their digests in an `artifacts` block), and writes `contract.snapshot.json`:
commit it with the manifest. See
`tera plugin pack -h`.

`pack --url` refuses a release whose `about {}` block names no licence:
`new` wrote `LicenseRef-Unset`. Edit `manifest.hcl` to name yours, as an SPDX
expression such as `Apache-2.0`, and check the publisher and description.

The `--url` is where the release will be published: here the GitHub release
the release workflow publishes on a `v<version>` tag, with `<owner>` yours.
`pack` writes a remote origin at it, and a runner fetches the release from
there itself. Without it `pack` writes a bundled origin, which only the
daemon can read: placed on a fleet runner, it is relayed there by the
daemon. The author's guide, `docs/ops/plugin-authoring.md`, walks the same
loop, and then the release.

## State, settings, the UI and events

As the ui template: the data directory is `$TERA_PLUGIN_DATA`; the configuration
is the installation's `config {}` block validated against `config_schema`; the
secret `api-token` is the installation's
`secret "api-token" { ref = "secret://ai-probe-api-token"  audience = "plugin" }`; the
UI is the web kit, acting as the person signed in under the
`read-for-a-person` grant; and `watch.go` watches the plugin's own Work
Order types, such as `note`, once the configuration names a feed.

## Acting on behalf of a person

`file_note` (`filing.go`) files a `note` Work Order for the person the tool call is
for, as that person. tera attaches a caller assertion to every tool call it
forwards, naming who the call is for, and the SDK verifies it
(`pluginsdk.VerifiedCaller`). The plugin exchanges that assertion at the token
endpoint on its tera socket for a token that acts for the person, with the web
kit's `webui.Exchange`, the same exchange the kit makes for the UI, and calls
`work_order.create` with it through the socket's `/mcp/<exposure>` gateway, the one
door such a token opens. The Work Order records the person as its creator and
this plugin as the way it was filed.

The manifest requests this as a grant, and nothing is granted by being
requested:

    grant "file-for-a-person" {
      on_behalf_of {
        verbs = ["work_order/create"]
        types = ["plugin.ai-probe/work-order-types/note"]
      }
    }

`plugin.ai-probe/…` there is the manifest naming its own type by the plugin's name: when
the installation's grant is compiled, tera resolves it to this installation's own
release address. The plugin's code never spells it — see below.

The installation approves it. The token then carries at most these verbs, on
these types, intersected with what the person holds. A call with no caller
assertion is for nobody: `file_note` refuses it and files nothing. The configuration
names the operator's Work Order exposure, and optionally the worker:

    config = {
      filing = { exposure = "<the Work Order exposure>" }
    }

## Shipping Work Order types in the plugin vault

`vault/.tera/` is the plugin's vault. tera mounts it under the installation's release
address, `plugin.<installation>.v<major>` — `plugin.ai-probe.v0.1` installed under its own
name at 0.1.0 — so `work-order-types/note.hcl` registers as
`plugin.ai-probe.v0.1/work-order-types/note`. The installation's name and the major are
tera's to choose, so the plugin's code never spells them: `file_note` files the type
by the key its start contract builds, `c.TypeKey("note")` (`start.Contract.TypeKey`).
Its session runs the vault's `note` tool
(`tools/note.hcl`, `tools/note/note.py`), which calls this plugin's `note` tool through
tera's gateway, at the exposure `plugin.ai-probe` tera derives from `serves { tools {} }`.
Its `credential { filer {} }` has the session present its per-dispatch token, which
acts as the person the Work Order was filed for.

- A vault file carries no `version` line: the manifest's `level "recipes"` is the one
  place the vault says which grammar it is in, and `pack` validates the whole
  vault at that level.
- A plugin vault carries only the kinds that do work: Work Order types, skills,
  tools, triggers and toolchains. Roles, role bindings, users and workers are
  refused: authority reaches a plugin only through its installation's approved
  grants.
- A plugin's triggers do not chain off each other's Work Orders: a Work Order
  one of this plugin's triggers filed does not fire another of its triggers.
- `tera plugin dev` mounts no vault, so under it the `note` type is not
  registered, and it passes no configuration, so `file_note` names the missing
  `filing.exposure`. Install the packed plugin to file a note.
